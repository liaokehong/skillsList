# clarify-first — 先想清楚，再动手

AI 执行不到位的根因大多不在执行，而在开工之前：需求里的名词没定义、"做好"没有可判定的标准、关键信息没核实就当成了事实。本 skill 强制在动手前完成对齐，产出一份《任务简报》作为执行契约。

本框架自己的失败模式是**过度流程**：小任务硬走全流程是浪费。第 0 步分诊就是防线。

## 第 0 步 · 分诊

| 档位 | 判据 | 走法 |
|---|---|---|
| 直做 | 意图单一、产物明确、做错重做成本分钟级（改错字、按明确指示改一处） | 跳过本框架 |
| 轻量 | 方向明确但有少量未定点（格式、命名、取值没说） | 一句话列出假设后直接做，交付时说明假设 |
| 全流程 | 下列信号 ≥2 个：① 需求含未定义名词（"工作台""系统""优化体验"）② "做好"无法一句话判定 ③ 存在多个可行方向 ④ 做错方向的返工成本 ≥ 半小时 | 走完以下五步，出简报 |

## 第 1 步 · 调研（先列清单，再查）

调研前先列**知识依赖清单**——"完成这个任务我需要知道什么"，逐项标注：

- 已核实（有出处）
- **在场未核实**（"我知道"但没验证过——这一类最容易蒙混过关，必须显式列出）
- 未知（需要查）

然后按三问查：

1. **问题域**：别人怎么解决这类问题？成熟方法论是什么？
2. **实现域**：产出物本身怎么做才好（格式、模板、平台约束）？
3. **查重**：是否已有现成方案/库/skill？有则借鉴，并写明自己的差异。

> 为什么调研在提问之前：问出好问题的前提是对问题域有基本认知。没调研过的问题都是空泛的，而且调研经常直接改变方案本身。

## 第 2 步 · 澄清（少问，问准）

- 只问"不问就会走偏"的问题，**≤3 个**，用结构化提问工具（AskUserQuestion），每题给出推荐选项和理由。
- 优先级 = 影响 × 不确定性：优先问高影响、高不确定的分叉点。
- 其余模糊点一律不问，写进简报的"关键假设"（默认成立，用户可纠正）。
- 定义完整性对照歧义清单：功能范围 / 数据与实体 / 交互流程 / 非功能要求（性能、安全）/ 外部依赖 / 边界与异常 / 术语一致 / 模糊形容词（"好用""稳定"必须量化）。

## 第 3 步 · 任务简报（执行契约）

```markdown
# 任务简报：<一句话任务>

## 我的理解
<把模糊需求翻译成具体定义：是什么、给谁用、解决什么问题>

## 范围
- 做：<...>
- 不做：<...>

## 关键假设
<未提问的次要模糊点，默认成立，可纠正>
1. ...

## 验收标准
<3~5 条，每条可独立判定 通过/不通过>
- [ ] ...

## 步骤
<有序，每步有明确产出>
1. ...

## 信息来源
| 关键事实 | 来源 | 状态 |
|---|---|---|
| ... | 链接 / 在场知识 / 推断 | 已核实 / 未核实 |
```

简报交给用户确认（或纠正假设）后才开工。同一任务内的后续小步不重复出简报。

## 第 4 步 · 执行与收尾

执行全程遵守**证据三来源**：

| 来源 | 处理方式 |
|---|---|
| 搜来的 | 标注链接 |
| 在场知识（训练记忆） | 显式列出、可检验；支撑关键决策前先抽查验证 |
| 无法核实的 | 显式标"未核实"，不得混入结论冒充确定 |

瞎编的：禁止。

完工对照（交付前过一遍）：

- [ ] 验收标准逐条检查，通过才交付
- [ ] 简报里承诺的范围没有悄悄缩水
- [ ] 执行中新增的未核实事实已标注
